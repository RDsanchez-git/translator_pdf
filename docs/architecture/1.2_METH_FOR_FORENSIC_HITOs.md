## 1. DEFINICIÓN Y NATURALEZA DE UN HITO

### 1.1 Definición

Un **HITO** —Hito de Auditoría Forense— es un documento de **evidencia forense pura** que registra observaciones, hallazgos, hipótesis, gaps y reconciliaciones del estado actual del repositorio frente a los contratos arquitectónicos vigentes.

Un HITO existe para responder:

1. **Qué es verdadero ahora** en el código, wiring, documentación o artefactos.
2. **Qué exige la arquitectura** según ADRs, NADRs, metodología o principios.
3. **Dónde difieren** el estado observado y el estado requerido.
4. **Qué permanece no resuelto** y debe convertirse en Decision Candidate, ADR, NADR, Execution Plan o finding diferido.

Un HITO **no diseña**, **no implementa** y **no prescribe código de producción**. Su valor es producir evidencia confiable para que las decisiones posteriores no se basen en intuición, memoria o sesgo de confirmación.

### 1.2 Naturaleza

| Atributo | Valor |
|---|---|
| **Naturaleza** | Read-only. No se propone código de producción. No se materializan decisiones de implementación. |
| **Estado documental** | `IN_PROGRESS` durante auditoría → `FROZEN` al cierre. |
| **Modificación tras FROZEN** | Prohibida. Correcciones requieren nueva versión o nuevo HITO de reconciliación. |
| **Ubicación canónica** | `docs/architecture/adr/phase-{fase}/00-foundation/` |
| **Nomenclatura canónica** | `HITO_{X.Y}_{NOMBRE_DESCRIPTIVO}.md` |
| **Referenciable desde** | ADRs, NADRs, Execution Plans, Findings Registers, Evidence Logs, Handoffs. |
| **Autoridad** | Evidencia forense. No reemplaza ADRs/NADRs. |
| **Relación con implementación** | Precede cualquier diseño o implementación que dependa de evidencia. |

> **Nota sobre extensión del concepto de HITO (v1.2.0):**
> La metodología general (`METHODOLOGY_FOR_ORDERED_PIPELINE_CHANGES.md` §3.5.1) define los HITOs como "HITOs de Auditoría Forense (Fase 0)". Esta metodología **extiende el concepto a todas las fases** porque el principio *Audit First, Design Later* aplica a toda decisión arquitectónica, no solo a la Fase 0.
>
> La evidencia forense es necesaria cuando:
> - Una sub-fase requiere discovery antes de diseñar (ej: HITO_2.0 para Fase 2).
> - Un gap requiere auditoría de cumplimiento antes de remediación (ej: HITO_3.x para Fase 3).
> - Una contradicción documentación/runtime requiere reconciliación formal.
>
> Esta extensión **no contradice** la metodología general; la complementa. Los HITOs de Fase 0 siguen siendo la base fundacional; los HITOs de sub-fases son la evidencia forense específica que cada fase necesita antes de diseñar.

### 1.3 Principio rector

> **Audit First, Design Later.**  
> No se escribe código sin Execution Plan aprobado.  
> No se escribe Execution Plan sin NADRs aprobados.  
> No se escriben NADRs sin evidencia forense suficiente.  
> Los HITOs son el mecanismo principal para producir esa evidencia.

### 1.4 Principio metodológico central: Observed ≠ Required ≠ Decision

Todo HITO debe separar explícitamente tres niveles epistemológicos:

| Nivel | Definición | Ejemplo |
|---|---|---|
| **Observed** | Lo que el código, wiring, tests, artefactos o documentación realmente hacen hoy. | `ManifestFingerprintCalculator` no incluye `ASTSchemaVersion` en el payload. |
| **Required** | Lo que exige una fuente normativa vigente: ADR Maestro, NADR, metodología o principios. | ADR Maestro exige desacoplar AST Schema Version, Corpus Version e Identity Hash. |
| **Decision** | Lo que una fase previa decidió, declaró como DONE o asumió. Puede ser correcto, incompleto o erróneo. | Fase 2 declara `ASTSchemaVersion` como dimensión diferenciada. |

**Regla:** Un HITO no puede inferir un gap solo porque algo requerido no aparece de inmediato. Debe primero clasificarlo como `TO BE VERIFIED`, investigar las hipótesis plausibles y luego reconciliar `Observed / Required / Decision`.

## 2. TIPOS DE HITO

| Tipo | Propósito | Ejemplo histórico o aplicable |
|---|---|---|
| **Forensic Flow Audit** | Auditar un flujo transaccional específico del sistema desde entry point hasta salida. | HITO_0.2 — Ground Truth & Sealing |
| **Gap Matrix** | Consolidar brechas entre estado observado y arquitectura objetivo. | HITO_0.5 Entregable 1 |
| **Discovery** | Discovery completo de una sub-fase con triaje, hipótesis, pilares y gaps. | HITO_2.0 — Scientific Baseline |
| **Compliance Audit** | Verificar cumplimiento de ADRs/NADRs/reglas normativas específicas. | HITO_3.x |
| **Dimension & Mutation Semantics Audit** | Auditar dimensiones observadas, participación en contratos y sensibilidad/insensibilidad ante mutaciones. | HITO_3.1 — Identity Dimension & Mutation Matrix |
| **Canonicalization / Determinism Audit** | Auditar serialización, ordering, framing, sentinels, estabilidad y superficie de colisión. | HITO_3.2 |
| **Invalidation / Lifecycle Audit** | Auditar qué mutaciones invalidan estado, sello, baseline, caché, artefactos o contratos de ejecución. | HITO_3.4 |
| **Reconciliation HITO** | Resolver contradicciones entre documentación, runtime, tests o HITOs previos. | HITO_x.y — Documentation vs Runtime Reconciliation |

## 3. ESTRUCTURA CANÓNICA DE UN HITO

Todo HITO debe usar una estructura estable. Las secciones marcadas como **obligatorias** deben aparecer siempre. Las secciones marcadas como **condicionales** se incluyen cuando aplican al tipo de HITO o al mandato del hito.

```text
# HITO_{X.Y}_{NOMBRE_DESCRIPTIVO}.md

## METADATA                                           [OBLIGATORIO]
## CHANGELOG                                          [OBLIGATORIO]

## 1. RESUMEN EJECUTIVO                               [OBLIGATORIO]
## 2. LÍMITE EPISTEMOLÓGICO Y MÉTODO FORENSE           [OBLIGATORIO]
## 3. ALCANCE AUDITADO                                [OBLIGATORIO]
## 4. FUENTES DE EVIDENCIA                            [OBLIGATORIO]

## 5. MAPA DE FLUJOS OBSERVADOS                       [CONDICIONAL: Flow Audit, Discovery]
## 6. INVENTARIO DE DIMENSIONES / COMPONENTES          [CONDICIONAL: Dimension Audit, Discovery]
## 7. MATRIZ OBSERVED / REQUIRED / DECISION            [CONDICIONAL: Compliance, Reconciliation]
## 8. MUTATION SEMANTICS MATRIX                        [CONDICIONAL: Mutation Semantics, Invalidation]
## 9. CANONICALIZATION / DETERMINISM AUDIT             [CONDICIONAL: Canonicalization]
## 10. REGISTRO DE EVIDENCIA FORENSE                   [OBLIGATORIO]
## 11. OBSERVACIONES COMPLEMENTARIAS                   [CONDICIONAL: si hay OBS]
## 12. MATRIZ DE TRIAJE                                [CONDICIONAL: Discovery]
## 13. MATRIZ DE PILARES                               [CONDICIONAL: Discovery, Compliance]
## 14. GAPS CONSOLIDADOS                               [OBLIGATORIO]
## 15. ESTADO DE HIPÓTESIS                             [CONDICIONAL: Discovery, Reconciliation]
## 16. RESPUESTAS A PREGUNTAS DEL MANDATO              [CONDICIONAL: si hay mandato]
## 17. VERIFICACIÓN DE CUMPLIMIENTO ADR/NADR           [CONDICIONAL: Compliance]
## 18. MATRIZ DE TRAZABILIDAD DC                       [CONDICIONAL: si hay Decision Candidates]
## 19. APÉNDICE NO NORMATIVO — RIESGOS                 [CONDICIONAL]
## 20. APÉNDICE NO NORMATIVO — PREGUNTAS PARA ADR      [CONDICIONAL]
## 21. CIERRE DEL HITO                                 [OBLIGATORIO]
```

**Regla de orden:** La estructura puede reducirse, pero no debe reordenarse sin justificación. El orden está diseñado para preservar la cadena epistemológica:

```text
Scope
  -> Evidence
  -> Observed behavior
  -> Reconciliation
  -> Gaps
  -> Questions / DCs
  -> Closure
```

> **Nota sobre proporcionalidad (v1.2.0):**
> La estructura de 21 secciones es la estructura **completa** para HITOs de alta complejidad (Discovery, Gap Matrix consolidada). Para HITOs más acotados, la estructura se reduce proporcionalmente:
>
> | Complejidad del HITO | Secciones típicas | Ejemplo |
> |---|---|---|
> | **Alta** (Discovery, Gap Matrix) | 15-21 secciones | HITO_2.0, HITO_0.5 |
> | **Media** (Compliance, Dimension Audit) | 10-15 secciones | HITO_3.1, HITO_3.3 |
> | **Baja** (Reconciliation, Flow Audit específico) | 6-10 secciones | HITO de reconciliación puntual |
>
> Las secciones obligatorias (Metadata, Changelog, Resumen, Límite Epistemológico, Alcance, Fuentes, Registro de Evidencia, Gaps, Cierre) siempre aparecen. Las secciones condicionales se incluyen solo cuando el tipo de HITO o el mandato las requieren.

## 4. SECCIONES OBLIGATORIAS — ESPECIFICACIÓN DETALLADA

### 4.1 Metadata

Todo HITO debe iniciar con metadata explícita.

```markdown
# HITO_{X.Y}_{NOMBRE_DESCRIPTIVO}.md

**Estado:** {IN_PROGRESS | FROZEN} v{X.Y.Z}
**Fecha de emisión:** {YYYY-MM-DD}
**Fecha de congelamiento:** {YYYY-MM-DD | N/A mientras IN_PROGRESS}
**Fase:** {Fase completa} — {Sub-fase} ({Nombre de la sub-fase})
**Tipo de artefacto:** {Forensic Discovery | Flow Audit | Gap Matrix | Compliance Audit | Dimension & Mutation Semantics Audit | Canonicalization Audit | Reconciliation HITO}
**Naturaleza:** Read-only. No se propone código de producción ni se materializan decisiones de implementación.
**Evidencia Forense Vinculante:** {Lista de HITOs previos, ADRs, NADRs, planes, registros, handoffs y módulos auditados}
**Mandato:** {Pregunta rectora o mandato del HITO}
**Síntesis:** {1-2 líneas de síntesis del HITO}
```

**Reglas:**

1. La metadata debe declarar el tipo de HITO.
2. La metadata debe declarar las fuentes vinculantes.
3. La metadata debe declarar si el documento está `IN_PROGRESS` o `FROZEN`.
4. Mientras esté `IN_PROGRESS`, `Fecha de congelamiento` debe ser `N/A`.

### 4.2 Changelog

```markdown
### Changelog

| Versión | Fecha | Cambio |
|---|---|---|
| 1.0.0-IN_PROGRESS | {YYYY-MM-DD} | Emisión inicial. |
| 1.0.0-FROZEN | {YYYY-MM-DD} | Cierre formal del HITO. |
```

**Reglas:**

1. Todo HITO debe tener changelog desde `1.0.0`.
2. Los IDs de evidencia, gaps, observaciones e hipótesis no se reasignan entre versiones.
3. Si un hallazgo se corrige, se marca como corregido o superseded, pero no se elimina silenciosamente.
4. Los HITOs históricos sin changelog se consideran excepciones heredadas, no precedente nuevo.

### 4.3 Resumen Ejecutivo

Debe responder exactamente:

1. **Qué se auditó.**
2. **Qué se encontró.**
3. **Qué implica para la fase o sub-fase.**

Debe contener:

- Hallazgo central en formato de cita.
- Defectos dominantes confirmados con referencias a evidencia.
- Veredicto forense.
- Estado de preparación para el siguiente documento.

Plantilla:

```markdown
## 1. RESUMEN EJECUTIVO

Se auditó {alcance}. La auditoría cubrió {módulos/superficies} y verificó {contratos/reglas}.

**Hallazgo central:**

> {Hallazgo central en una frase precisa}

**Defectos dominantes confirmados:**

1. **{Defecto 1} ({E-ID}):** {Resumen}.
2. **{Defecto 2} ({E-ID}):** {Resumen}.
3. **{Defecto 3} ({E-ID}):** {Resumen}.

**Veredicto:** {Conclusión operacional del HITO}.
```

**Regla:** El resumen ejecutivo no debe exceder una página salvo que el HITO sea una Gap Matrix consolidada.

### 4.4 Límite Epistemológico y Método Forense

Todo HITO debe declarar qué puede y qué no puede concluir.

```markdown
## 2. LÍMITE EPISTEMOLÓGICO Y MÉTODO FORENSE

### 2.1 Límite epistemológico

Este HITO es read-only. No propone implementación. No decide diseño. No crea entidades. No modifica código. Su función es observar, clasificar y reconciliar evidencia.

### 2.2 Método forense

La auditoría siguió el método:

1. Cargar fuentes normativas.
2. Cargar HITOs previos aplicables.
3. Inspeccionar runtime/código/artefactos.
4. Separar Observed / Required / Decision.
5. Registrar evidencia estable.
6. Consolidar gaps solo cuando exista discrepancia demostrada.
7. Declarar `TO BE VERIFIED` cuando la evidencia sea insuficiente.
8. Derivar Decision Candidates solo si la evidencia los exige.
```

### 4.5 Alcance Auditado

```markdown
## 3. ALCANCE AUDITADO

| Superficie | Módulos | Estado |
|---|---|---|
| `{ruta/modulo/}` | {lista de archivos} | {100% | Parcial | Referenciado | No auditado} |
```

Debe separar:

| Categoría | Definición |
|---|---|
| **Auditado** | Inspeccionado directamente en este HITO. |
| **Referenciado** | Usado por evidencia previa, no re-auditado. |
| **Fuera de scope** | Explícitamente excluido del HITO. |
| **No verificable** | Requiere runtime, disco, artefactos externos o ejecución no disponible. |

**Regla:** Ningún hallazgo puede basarse en una superficie no auditada sin declararlo como evidencia indirecta.

### 4.6 Fuentes de Evidencia

```markdown
## 4. FUENTES DE EVIDENCIA

| Tipo | Fuente | Uso en el HITO |
|---|---|---|
| ADR | `{ruta}` | Fuente normativa |
| NADR | `{ruta}` | Regla normativa |
| HITO previo | `{ruta}` | Evidencia forense heredada |
| Código | `{ruta}` | Observación runtime/código |
| Test | `{ruta}` | Verificación comportamental |
| Handoff | `{ruta}` | Estado de fase previa |
```

**Regla:** Cada fuente debe clasificarse como normativa, forense, runtime, histórica o contextual.

### 4.7 Registro de Evidencia Forense

**Nomenclatura:**

```text
E-{FASE}.{HITO_SECUENCIA}-{NNN}
```

Ejemplos:

```text
E-0.2-001
E-2.0-015
E-3.1-003
```

**Formato resumido:**

```markdown
## 10. REGISTRO DE EVIDENCIA FORENSE

IDs normalizados y estables. Severidad: P0 = bloquea certificación, P1 = defecto estructural, P2 = riesgo latente.

| ID | Sev | Evidencia (archivo → código) | Hallazgo |
|---|---|---|---|
| **E-{X.Y}-{NNN}** | {P0/P1/P2} | `{archivo}::{símbolo}` → `{código observado}` | **{Título}.** {Descripción forense}. |
```

**Formato extendido para hallazgos P0/P1:**

```markdown
### Evidencia E-{X.Y}-{NNN}: {Título}

* **Archivo Fuente Primario:** `{ruta}`
* **Símbolo Auditado:** `{clase/método/función}`
* **Declaración Observada:**

```python
{fragmento mínimo suficiente}
```

* **Observed:** {Qué hace el código}
* **Required:** {Qué exige ADR/NADR/metodología}
* **Decision:** {Qué decidió una fase previa, si aplica}
* **Hallazgo Forense:** {Conclusión basada en evidencia}
* **Consecuencia Arquitectónica:** {Impacto}
* **Estado:** {OPEN | RESOLVED | TO BE VERIFIED | DEFERRED}
```

**Reglas:**

1. Todo hallazgo debe tener ID estable.
2. Toda evidencia debe apuntar a archivo y símbolo cuando sea código.
3. Si no hay símbolo específico, debe explicarse por qué.
4. Toda evidencia debe tener severidad.
5. Toda evidencia debe separar `Observed / Required / Decision` cuando aplique.
6. No se registran inferencias especulativas como evidencia. Se registran como hipótesis.

### 4.8 Gaps Consolidados

**Nomenclatura:**

```text
GAP-{FASE}.{HITO_SECUENCIA}-{NN}
```

Ejemplos:

```text
GAP-0.2-01
GAP-2.0-05
GAP-3.1-002
```

**Formato:**

```markdown
## 14. GAPS CONSOLIDADOS

| GAP | Descripción | Evidencia | Pilar / Contrato | Fase destino | Estado |
|---|---|---|---|---|---|
| **GAP-{X.Y}-{NN}** | {Descripción} | {E-{X.Y}-{NNN}} | {Pilar/NADR/ADR} | **{Fase destino}** | {OPEN | DEFERRED | BLOCKING} |
```

**Reglas:**

1. Todo GAP debe tener evidencia vinculada.
2. Todo GAP debe tener fase destino explícita.
3. Todo GAP debe indicar el contrato o pilar afectado.
4. Un GAP no puede derivarse solo de una preferencia de diseño.
5. Si el estado es incierto, debe registrarse como `TO BE VERIFIED`, no como GAP.
6. Un GAP sin fase destino es defecto del HITO.

### 4.9 Cierre del HITO

```markdown
## 21. CIERRE DEL HITO {X.Y}

Este HITO confirma que {veredicto final}.

**Estado del HITO:** FROZEN v{X.Y.Z}
**Condición de cierre cumplida:** {Lista de condiciones verificadas}
**Verificación de cadena de gobernanza:** {Cadena completa verificada}
**Contradicciones con HITOs previos:** {Ninguna | Listadas y reconciliadas}
**Decision Candidates generados:** {Ninguno | Lista}
**Siguiente paso recomendado:** {Qué documento se construye con este HITO como insumo}
```

## 5. SECCIONES CONDICIONALES — ESPECIFICACIÓN DETALLADA

### 5.1 Mapa de Flujos Observados

Aplica a Flow Audit y Discovery.

```text
FLUJO {LETRA} -- {Nombre del flujo}

  {entry point}
    -> {componente 1} [{estado}]
    -> {componente 2} [{estado}]
    -> {componente 3} [{estado}]
    -> {salida}

Leyenda:
  [OK] flujo sano observado
  [GAP] gap confirmado
  [RISK] riesgo latente
  [TBD] requiere verificación adicional
```

**Reglas:**

1. Debe mostrar entry point, use case, servicios, puertos, persistencia y salida cuando existan.
2. Debe marcar puntos sanos y defectuosos.
3. No debe ocultar bifurcaciones relevantes.
4. Debe indicar qué evidencia respalda cada defecto del flujo.

### 5.2 Inventario de Dimensiones / Componentes

Aplica a Discovery, Dimension Audit y Mutation Semantics Audit.

```markdown
## 6. INVENTARIO DE DIMENSIONES / COMPONENTES

| Dimensión / Componente | Representación observada | Participa en contrato | Semántica | Estado |
|---|---|---|---|---|
| {Nombre} | `{clase/campo/servicio}` | {Sí/No/Parcial/No visible} | {Descripción} | {CONFIRMADO | TO BE VERIFIED | MISSING | OUT-OF-SCOPE} |
```

**Reglas:**

1. El inventario debe distinguir entidad, campo, constante, convención, documentación y representación indirecta.
2. No se declara `MISSING` hasta agotar hipótesis razonables.
3. Si la representación es indirecta, debe evaluarse su suficiencia contra el contrato normativo.

### 5.3 Matriz Observed / Required / Decision

Aplica a Compliance Audit y Reconciliation HITO.

```markdown
## 7. MATRIZ OBSERVED / REQUIRED / DECISION

| Tema | Observed | Required | Decision previa | Estado | Evidencia |
|---|---|---|---|---|---|
| {Tema} | {Qué hace el código} | {Qué exige la arquitectura} | {Qué decidió fase previa} | {COMPLIANT | DISCREPANCY | TO BE VERIFIED} | {E-ID / fuente} |
```

**Reglas:**

1. `Observed` debe provenir de código, tests, artefactos o runtime.
2. `Required` debe provenir de ADR, NADR, metodología o principios.
3. `Decision` debe provenir de documentos de fase, handoff, plan o findings register.
4. Si los tres niveles no pueden completarse, el estado debe ser `TO BE VERIFIED`.

### 5.4 Mutation Semantics Matrix

Aplica a Mutation Semantics Audit, Invalidation Audit, Identity Audit, Canonicalization Audit y cualquier HITO que evalúe sensibilidad a cambios.

```markdown
## 8. MUTATION SEMANTICS MATRIX

| Mutación | Dimensión A | Dimensión B | Dimensión C | Identidad cambia? | Estado/sello queda válido? | Observed behavior | Required behavior | Evidencia | Gap |
|---|---|---|---|---|---|---|---|---|---|
| {Mutación} | {Sí/No/?} | {Sí/No/?} | {Sí/No/?} | {Sí/No/A DECIDIR} | {Sí/No/A DECIDIR} | {Qué ocurre hoy} | {Qué debería ocurrir} | {E-ID} | {GAP-ID o None} |
```

**Reglas:**

1. Las celdas con `?` deben resolverse mediante evidencia o marcarse como `TO BE VERIFIED`.
2. Las celdas `A DECIDIR` no son defectos por sí mismas; son candidatos a decisión.
3. Si al cierre del HITO queda `A DECIDIR`, debe listarse en Decision Candidates o Deferred Questions.
4. La matriz debe separar comportamiento observado de comportamiento requerido.
5. La matriz no debe proponer implementación.
6. En identity/canonicalization audits, debe distinguir:
   - mutación que cambia identidad,
   - mutación que invalida sello,
   - mutación que requiere re-sellado,
   - mutación irrelevante que no debe alterar la identidad.

### 5.5 Canonicalization / Determinism Audit

Aplica a auditorías de hashing, serialización, ordenamiento y formatos canónicos.

```markdown
## 9. CANONICALIZATION / DETERMINISM AUDIT

| Superficie | Regla observada | Riesgo | Evidencia | Estado |
|---|---|---|---|---|
| Ordering | {Cómo se ordena} | {No determinismo / estable} | {E-ID} | {OK | GAP | TO BE VERIFIED} |
| Framing | {Cómo se delimitan campos} | {Colisión / ambigüedad} | {E-ID} | {OK | GAP | TO BE VERIFIED} |
| Sentinel values | {Valores especiales} | {Colisión semántica} | {E-ID} | {OK | GAP | TO BE VERIFIED} |
| Encoding | {UTF-8/JSON/etc.} | {Divergencia} | {E-ID} | {OK | GAP | TO BE VERIFIED} |
| Hash algorithm | {SHA-256/etc.} | {Obsoleto / correcto} | {E-ID} | {OK | GAP | TO BE VERIFIED} |
```

**Reglas:**

1. Debe auditar ordering.
2. Debe auditar delimitadores o framing.
3. Debe auditar sentinels.
4. Debe auditar encoding.
5. Debe auditar estabilidad ante reordenamientos irrelevantes.
6. Debe auditar sensibilidad ante mutaciones relevantes.
7. No debe reemplazar el formato por intuición; debe demostrar el riesgo.

### 5.6 Observaciones Complementarias

```markdown
## 11. OBSERVACIONES COMPLEMENTARIAS

| ID | Observación | Impacto | Estado |
|---|---|---|---|
| OBS-{X.Y}-{NN} | {Observación} | {Bajo/Medio/Alto} | {OPEN | DEFERRED | CLOSED} |
```

**Regla:** Una OBS no es un GAP. Si tiene consecuencia arquitectónica demostrada, debe promoverse a GAP.

### 5.7 Matriz de Triaje

Aplica a Discovery.

| Clasificación | Definición |
|---|---|
| **RETAIN** | Reutilizable conceptualmente. No requiere cambio de responsabilidad o contrato. |
| **REFACTOR** | No retenible sin cambio de responsabilidad, contrato o invariantes. |
| **RELOCATE** | Ubicación incorrecta; frontera hexagonal o bounded context violado. |
| **DEPRECATE** | Duplicado, obsoleto o sin consumidores. |
| **MISSING** | Capacidad inexistente demostrada. |
| **OUT-OF-SCOPE** | Fuera de la sub-fase actual, registrado para trazabilidad. |
| **TO BE VERIFIED** | Evidencia insuficiente; no se puede clasificar aún. |

Formato:

```markdown
## 12. MATRIZ DE TRIAJE

| Componente | Clasificación | Justificación forense |
|---|---|---|
| `{NombreComponente}` | {RETAIN/REFACTOR/RELOCATE/DEPRECATE/MISSING/OUT-OF-SCOPE/TO BE VERIFIED} | {Justificación con referencia a evidencia} |
```

### 5.8 Matriz de Pilares

Aplica a Discovery y Compliance.

```markdown
## 13. MATRIZ DE PILARES

### Pilar {N} -- {Nombre del pilar}

| Elemento | Estado | Evidencia |
|---|---|---|
| {Elemento} | {EXISTENTE | PARCIAL | FALTANTE | TO BE VERIFIED | OUT-OF-SCOPE} | {Referencia} |

**Veredicto del pilar:** {Síntesis}
```

**Regla:** Los pilares deben derivarse del mandato del HITO, ADR Maestro, NADRs o fase activa. No se inventan pilares ad hoc sin fuente.

### 5.9 Estado de Hipótesis

Aplica a Discovery y Reconciliation.

```markdown
## 15. ESTADO DE HIPÓTESIS DEL DISCOVERY

| ID | Hipótesis | Veredicto | Evidencia | Implicación |
|---|---|---|---|---|
| H-{X.Y}-{LETRA} | {Hipótesis} | {CONFIRMADA | RESUELTA | NO VERIFICABLE | RECHAZADA} | {E-ID} | {Impacto} |
```

| Veredicto | Definición |
|---|---|
| **CONFIRMADA** | La evidencia demuestra que la hipótesis es verdadera. |
| **RESUELTA** | La evidencia demuestra que la hipótesis era falsa o que el problema ya está resuelto. |
| **RECHAZADA** | La evidencia contradice la hipótesis. |
| **NO VERIFICABLE** | No se puede verificar desde los medios disponibles; requiere disco, runtime, entorno externo o decisión humana. |

**Regla:** Un HITO no puede pasar a `FROZEN` con hipótesis abiertas. Deben cerrarse como `CONFIRMADA`, `RESUELTA`, `RECHAZADA` o `NO VERIFICABLE`.

### 5.11 Verificación de Cumplimiento ADR/NADR

Aplica a Compliance Audit.

```markdown
## 17. VERIFICACIÓN DE CUMPLIMIENTO ADR/NADR

| Regla | Fuente | Required | Observed | Estado | Evidencia |
|---|---|---|---|---|---|
| {R1} | {NADR/ADR} | {Requisito} | {Código actual} | {PASS | FAIL | PARTIAL | TO BE VERIFIED} | {E-ID} |
```

**Reglas:**

1. `PASS` requiere evidencia positiva.
2. `FAIL` requiere discrepancia demostrada.
3. `PARTIAL` requiere cumplimiento incompleto demostrado.
4. `TO BE VERIFIED` requiere hipótesis abierta o evidencia insuficiente.

## 6. NOMENCLATURA CANÓNICA

### 6.1 IDs de HITO

```text
HITO_{FASE}.{SECUENCIA}_{NOMBRE_DESCRIPTIVO}.md
```

Ejemplos:

```text
HITO_0.1_REPOSITORY_ARCHITECTURE_INVENTORY.md
HITO_0.5_ENTREGABLE_1_GAP_MATRIX.md
HITO_2.0_SCIENTIFIC_BASELINE_DISCOVERY.md
HITO_3.1_IDENTITY_DIMENSION_MUTATION_MATRIX.md
```

### 6.2 Nota sobre `{FASE}` en contexto 17-BIS

En el contexto de Fase 17-BIS, `{FASE}` se refiere al número de sub-fase dentro de 17-BIS:

| ID | Significado |
|---|---|
| `0.x` | Fase 0 — Architecture & Baseline Audit Gate |
| `1.x` | Fase 1 — Pipeline / NADR Implementation |
| `2.x` | Fase 2 — Scientific Baseline Domain |
| `3.x` | Fase 3 — Identity & Trust Model |
| `4.x` | Fase 4 — Scientific Verification |
| `5.x` | Fase 5 — Baseline Certification |
| `6.x` | Fase 6 — Continuous Verification |

Ejemplo:

```text
E-3.1-003 = Evidencia 003 del HITO 3.1, dentro de Fase 17-BIS / Fase 3.
```

### 6.3 IDs de Evidencia

```text
E-{FASE}.{HITO_SECUENCIA}-{NNN}
```

Ejemplos:

```text
E-0.2-001
E-2.0-015
E-3.1-003
```

**Regla:** Usar tres dígitos para nuevos HITOs (`001`, `002`, `003`). Se toleran IDs históricos con dos dígitos.

### 6.4 IDs de Gaps

```text
GAP-{FASE}.{HITO_SECUENCIA}-{NN}
```

Ejemplos:

```text
GAP-0.2-01
GAP-2.0-05
GAP-3.1-002
```

**Regla:** Usar dos o tres dígitos de forma consistente dentro de un mismo HITO.

### 6.5 IDs de Observaciones

```text
OBS-{FASE}.{HITO_SECUENCIA}-{NN}
```

Ejemplos:

```text
OBS-2.0-01
OBS-3.1-003
```

### 6.6 IDs de Hipótesis

```text
H-{FASE}.{HITO_SECUENCIA}-{LETRA}
```

Ejemplos:

```text
H-2.0-A
H-3.1-B
```

### 6.7 IDs de Findings internos del HITO

Cuando el HITO necesite findings de nivel documental:

```text
H{FASE}.{HITO_SECUENCIA}-{NN}
```

Ejemplos:

```text
H3.1-01
H2.0-03
```

**Uso recomendado:** Findings de reconciliación, contradicciones documento/runtime o hallazgos que agrupan múltiples evidencias.

## 7. SEVERIDAD Y DECISION SCOPE

### 7.1 Severidad P0/P1/P2

| Severidad | Definición | Ejemplos |
|---|---|---|
| **P0** | Bloquea certificación, viola invariante del ADR Maestro, compromete identidad, determinismo, atomicidad, integridad o seguridad transaccional. | Partial sealing, hash insensible a mutación relevante, corrupción de baseline. |
| **P1** | Defecto estructural. Viola ENGINEERING_PRINCIPLES, NADR, Clean Architecture, bounded context, fail-fast o contrato tipado. | Duplicación de autoridad, composición inline prohibida, puerto mixto read/write. |
| **P2** | Riesgo latente o deuda controlada. No hay evidencia de explotación hoy, pero puede afectar mantenibilidad, observabilidad o evolución. | Mutabilidad profunda no explotada, docstring incorrecto, nomenclatura ambigua. |

**Regla:** La severidad debe basarse en consecuencia demostrada, no en preferencia estética.

### 7.2 Decision Scope

Aplica especialmente a Gap Matrix.

| Scope | Definición |
|---|---|
| **SYSTEMIC** | Impacta infraestructura global, firmas criptográficas, modelo de persistencia, plano de control, baseline o CI Gates. |
| **CROSS-CUTTING** | Afecta múltiples subsistemas, bounded contexts o transferencia de datos entre capas. |
| **LOCAL** | Afecta exclusivamente la lógica interna de un componente o etapa delimitada. |

## 8. CRITERIOS DE CIERRE FROZEN

Un HITO puede pasar a `FROZEN` solo si cumple todas las condiciones aplicables.

### 8.1 Checklist obligatorio

- [ ] Metadata completa y consistente.
- [ ] Changelog actualizado a la versión de cierre.
- [ ] Límite epistemológico declarado.
- [ ] Alcance auditado completo.
- [ ] Fuentes de evidencia listadas.
- [ ] 100% de módulos del alcance auditados o explícitamente marcados como `No verificable`.
- [ ] Todas las evidencias tienen ID estable.
- [ ] Todas las evidencias tienen severidad clasificada.
- [ ] Todas las evidencias relevantes separan `Observed / Required / Decision`.
- [ ] Todos los gaps tienen evidencia vinculada.
- [ ] Todos los gaps tienen fase destino explícita.
- [ ] Todas las hipótesis están cerradas como `CONFIRMADA`, `RESUELTA`, `RECHAZADA` o `NO VERIFICABLE`.
- [ ] Cero hipótesis abiertas.
- [ ] Cero contradicciones no documentadas con HITOs previos.
- [ ] Toda contradicción con HITO previo está reconciliada o marcada como finding emergente.
- [ ] Todos los IDs `E`, `GAP`, `OBS`, `H` son estables y no se reasignan.
- [ ] Resumen ejecutivo completo con hallazgo central y veredicto.
- [ ] Declaración de cierre con garantías explícitas.
- [ ] Cadena de gobernanza verificada.
- [ ] Siguiente paso recomendado declarado.

### 8.2 Regla sobre `TO BE VERIFIED`

Un HITO puede cerrar con elementos `TO BE VERIFIED` solo si:

1. No bloquean el cierre del mandato del HITO.
2. Están listados en Deferred Questions o Decision Candidates.
3. Tienen razón explícita de no resolución.
4. Tienen destino documental o fase destino.

### 8.3 Regla sobre `A DECIDIR`

Una celda o conclusión `A DECIDIR` debe convertirse en:

| Destino | Uso |
|---|---|
| **Decision Candidate** | Si requiere decisión arquitectónica. |
| **Deferred Question** | Si requiere evidencia adicional. |
| **Finding Register** | Si se difiere por scope. |
| **GAP** | Si hay discrepancia demostrada contra contrato vigente. |

## 9. CADENA DE TRAZABILIDAD

### 9.1 Cadena de gobernanza completa

```text
ADR Maestro
  -> ADR de Fase / ADR base
  -> HITOs de auditoría
  -> Gap Matrix / Evidence Register
  -> Decision Candidates
  -> Complexity Assessment
  -> ADR adicional, si aplica
  -> NADRs
  -> Execution Plan
  -> Implementación
  -> Tests / Evidence Log
  -> Handoff
```

### 9.2 Referencias obligatorias en un HITO

Todo HITO debe declarar:

1. Evidencia Forense Vinculante.
2. Módulos auditados.
3. Módulos referenciados pero no re-auditados.
4. ADRs/NADRs aplicables.
5. HITOs previos relevantes.
6. Hallazgos diferidos heredados, si aplican.

### 9.3 Regla de no-regresión

Un HITO de sub-fase no puede contradecir un HITO previo sin evidencia explícita.

Si encuentra contradicción, debe:

1. Documentar la contradicción.
2. Referenciar el HITO o documento contradicho.
3. Proveer evidencia nueva.
4. Reconciliar `Observed / Required / Decision`.
5. Registrar la resolución como finding emergente o gap de documentación/runtime.

### 9.4 Regla de reutilización

Antes de crear un HITO nuevo, debe verificarse si existe un HITO previo que cubra total o parcialmente el mismo dominio.

Si existe, el nuevo HITO debe:

1. Declararlo como insumo.
2. Explicar qué cambió desde entonces.
3. No duplicar inventarios sin necesidad.
4. Enfocarse en delta, reconciliación o nueva evidencia.

### 9.5 Flujo de hallazgos hacia Findings Register y Evidence Log (v1.2.0)

Los hallazgos de un HITO se clasifican en dos categorías según su naturaleza y destino:

```text
HITO (evidencia forense pura)
  │
  ├── Hallazgos que son evidencia pura (E-IDs)
  │     Permanecen en el HITO como evidencia forense.
  │     No requieren acción directa.
  │     Referenciados por Evidence Log como fuente.
  │
  ├── Gaps que requieren acción (GAP-IDs)
  │     Se trasladan al Deferred Findings Register de la fase activa.
  │     Clasificados como IMPLEMENTATION_REQUIRED, RECLASSIFIED_FUTURE_PHASE, etc.
  │     El Findings Register rastrea: hallazgo -> batch -> commit.
  │
  ├── Decision Candidates (DCs)
  │     Se trasladan al ADR/NADR correspondiente.
  │     El HITO los lista; el ADR/NADR los resuelve normativamente.
  │
  └── Deferred Questions
        Se registran en el Findings Register o en el Execution Plan
        como items pendientes de evidencia adicional.
```

**Relación con el Evidence Log de la fase:**

El `FASE_{X}_EXIT_REVIEW_EVIDENCE_LOG.md` (definido en METHODOLOGY §3.5.2) referencia los HITOs como **evidencia forense vinculante**. Cada entrada del Evidence Log debe contener una referencia al HITO y a los E-IDs específicos que fundamentan la clasificación del finding.

**Relación con el Findings Register de la fase:**

El `FASE_{X}_DEFERRED_FINDINGS_REGISTER.md` (definido en METHODOLOGY §3.5.3) consume los GAPs y Decision Candidates del HITO. Cada entrada del Findings Register debe referenciar el GAP-ID o DC del HITO que lo originó.

**Regla:** El HITO es la **fuente** de evidencia. El Evidence Log es la **justificación forense** de las clasificaciones. El Findings Register es la **trazabilidad operativa** de hallazgos a commits. Los tres documentos son complementarios y no se superponen.

## 10. ANTI-PATRONES PROHIBIDOS

| Anti-patrón | Descripción | Corrección |
|---|---|---|
| **HITO sin evidencia forense** | Hallazgos sin referencia a archivo, símbolo, test, documento o artefacto. | Todo hallazgo debe tener evidencia vinculada. |
| **HITO con propuestas de código** | El HITO prescribe implementación concreta. | Las propuestas van en ADRs, NADRs o Execution Plans. |
| **Diseño disfrazado de auditoría** | El documento parte de una solución y busca justificarla. | Formular hipótesis y auditar evidencia antes de decidir. |
| **Confundir Observed/Required/Decision** | Mezcla lo que el código hace con lo que la arquitectura exige o lo que una fase declaró. | Separar explícitamente los tres niveles. |
| **Declarar GAP prematuramente** | Se declara ausencia sin inspeccionar hipótesis razonables. | Usar `TO BE VERIFIED` hasta completar auditoría. |
| **HITO sin fase destino en Gaps** | Gaps sin asignación de fase o destino documental. | Todo GAP debe tener fase destino explícita. |
| **HITO sin severidad** | Evidencia sin P0/P1/P2. | Toda evidencia debe tener severidad. |
| **HITO sin cadena de gobernanza** | No conecta con ADRs/NADRs/HITOs previos. | Declarar cadena de gobernanza en metadata y cierre. |
| **HITO con hipótesis abiertas al FROZEN** | Hipótesis sin veredicto al cierre. | Cerrar como CONFIRMADA/RESUELTA/RECHAZADA/NO VERIFICABLE. |
| **HITO sin changelog** | No registra evolución del documento. | Todo HITO debe tener changelog desde v1.0.0. |
| **IDs inestables** | IDs cambian entre versiones. | IDs estables; nunca reasignar. |
| **Re-auditoría duplicada** | Repite trabajo de HITOs previos sin delta. | Reutilizar HITO previo y auditar cambios. |
| **Scope creep** | El HITO deriva hacia fases futuras no mandatadas. | Registrar out-of-scope y diferir. |
| **Overclaiming** | Conclusiones más fuertes que la evidencia. | Ajustar estado a evidencia: CONFIRMADO, PARCIAL, TO BE VERIFIED. |
| **No distinguir runtime histórico de runtime actual** | Mezcla código antes/después de una fase. | Separar runtime actual, runtime histórico y documentación. |

## 13. PRINCIPIO DE MÍNIMA DOCUMENTACIÓN

No se crea un HITO nuevo a menos que elimine una ambigüedad que esté bloqueando activamente:

1. una decisión arquitectónica,
2. una NADR,
3. un Execution Plan,
4. una implementación,
5. una certificación de baseline,
6. una reconciliación documentación/runtime,
7. una verificación de cumplimiento.

Antes de crear un HITO, se debe responder:

| Pregunta | Si la respuesta es NO |
|---|---|
| ¿Existe una ambigüedad real? | No crear HITO. |
| ¿La ambigüedad bloquea una decisión o ejecución? | No crear HITO. |
| ¿Hay evidencia nueva que no esté en HITOs previos? | Reutilizar HITO previo. |
| ¿El HITO tendrá cierre verificable? | No crear HITO todavía. |

## 14. EVOLUCIÓN DE LA METODOLOGÍA

### 14.1 Cuándo puede evolucionar

Esta metodología puede evolucionar cuando:

1. Se identifica un defecto recurrente en HITOs reales.
2. Un HITO no logra servir como insumo suficiente para ADR/NADR.
3. Hay ambigüedad de estructura que provoca re-trabajo.
4. Un Architecture Board solicita una mejora formal.
5. La metodología general superior cambia.

### 14.2 Proceso de cambio

1. Registrar el defecto metodológico.
2. Proponer cambio con ejemplo.
3. Validar contra HITOs históricos.
4. Aprobar por Architecture Board.
5. Publicar nueva versión SemVer.
6. No reescribir HITOs FROZEN salvo necesidad explícita.

### 14.3 Prohibición de meta-gobernanza infinita

No se crean documentos adicionales para gobernar cómo se crean HITOs. Este documento es el nivel máximo de meta-gobernanza para HITOs. Cualquier necesidad adicional se resuelve con una sección adicional aquí o con un apéndice.

- resistentes a sesgo de confirmación,
- compatibles con la metodología general,
